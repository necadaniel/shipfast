# Team Collaboration - Implementation Plan

## Overview

Enable secure sharing of projects and environment variables between team members with role-based access control.

---

## Core Concepts

### Team Structure

- **Team Owner**: User who created the team (usually the paying customer)
- **Team Members**: Invited users with different permission levels
- **Projects**: Can be owned by individual or shared with team
- **Permissions**: Role-based access at project level

### Key Principle

- Each user maintains their own encryption key (zero-knowledge)
- Shared projects use project-specific encryption keys
- Project keys are encrypted per-user and stored separately

## Encryption Strategy

### Problem: How do multiple users decrypt the same variables?

**Solution: Project-Level Encryption Keys**

1. **Personal Projects** (current implementation):

   - Variables encrypted with user's master key
   - Only that user can decrypt

2. **Team Projects** (new):
   - Each project gets its own encryption key (project key)
   - Project key is encrypted with each team member's master key
   - Stored in `ProjectShare.encryptedProjectKey`
   - When user accesses project, they decrypt the project key with their master key
   - Then use project key to decrypt variables

**Flow:**

```
1. Owner creates team project
   → Generate random project encryption key
   → Encrypt project key with owner's master key
   → Store in project.sharedWith[]

2. Owner invites team member
   → Fetch project key (decrypt with owner's key)
   → Encrypt project key with new member's master key
   → Store in project.sharedWith[] for new member

3. Member accesses project
   → Fetch their encrypted project key from project.sharedWith[]
   → Decrypt project key using their master key
   → Use project key to decrypt variables
```

   - Email, Role, Sent date, "Resend" / "Cancel" actions

4. **Shared Projects**
   - List of projects shared with team
   - Quick view of who has access
   - Link to project detail page

**Invite Flow:**

```
1. Click "Invite Member"
2. Modal opens:
   - Email input (with validation)
   - Role selector (Admin / Member / Viewer)
   - Optional: Personal message
3. Send invite → Email sent with magic link using fromNoReply email from `config.ts`
4. Recipient clicks link → Creates account (if new) → Joins team
5. Owner re-encrypts all shared project keys for new member
```

**In Project Detail Page:**

- Add "Share" button in header

  - Toggle: "Share with Team" (if team exists)

**Permissions:**

## API Endpoints Needed

### Team Management

```typescript
// Create team (owner only)
POST / api / team;
Body: {
  name: string;
}

// Get team details
GET / api / team;

// Update team
PATCH / api / team;
Body: {
  name: string;
}

// Delete team (owner only)
DELETE / api / team;
```

### Team Members

```typescript
// Invite member
POST /api/team/members
Body: { email: string, role: 'admin' | 'member' | 'viewer' }

// Update member role
PATCH /api/team/members/[userId]
Body: { role: string }

// Remove member
DELETE /api/team/members/[userId]

// Accept invitation (via magic link token)
POST /api/team/join
Body: { token: string }
```

### Project Sharing

```typescript
// Share project with team
POST /api/projects/[id]/share/team
Body: { permission: 'admin' | 'write' | 'read' }

// Share project with individual
POST /api/projects/[id]/share
Body: {
  email: string,
  permission: 'admin' | 'write' | 'read',
  encryptedProjectKey: string
}

// Update share permission
PATCH /api/projects/[id]/share/[userId]
Body: { permission: string }

// Revoke share
DELETE /api/projects/[id]/share/[userId]

// Get project key (for decryption)
GET /api/projects/[id]/key
Response: { encryptedProjectKey: string }
```

## Security Considerations

1. **Key Re-encryption Overhead**

   - When adding team member, need to re-encrypt ALL shared project keys
   - Consider background job for large teams
   - Show progress indicator to user

2. **Permission Checks**

   - Every API call must verify user has permission
   - Check at both project level and team level
   - Cache permissions for performance

3. **Revocation**

   - When removing member, immediately invalidate their access
   - Consider rotating project keys on member removal (paranoid mode)
   - Audit log for accountability

4. **Zero-Knowledge Preservation**
   - Server never sees decrypted project keys
   - All key encryption happens client-side
   - Backend only stores encrypted blobs
